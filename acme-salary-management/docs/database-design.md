# Database design (PostgreSQL)

```
countries ─┐                    ┌─ users ──< audit_logs
           ├──< employees >─────┤
departments┘     │  ▲ manager_id (self FK)
                 │
                 ├── 1:1 ── compensation   (current pay)
                 └── 1:N ── salary_history (append-only ledger) ──> users (changed_by)

exchange_rates (standalone, read at query time)
```

## Tables
| Table | Purpose | Key columns |
|---|---|---|
| `countries` | Reference. | `code` (ISO-2, unique), `name` (unique), `default_currency` ∈ INR/USD/EUR |
| `departments` | Reference. | `name` (unique) |
| `employees` | People. | `employee_code` (unique), `email` (unique), names, `phone`, `country_id`, `department_id`, `designation`, `employment_type`, `joining_date`, `status`, `manager_id` → employees |
| `compensation` | **Current** pay, one row per employee. | `employee_id` (unique FK), `amount NUMERIC(14,2)`, `currency`, `frequency`, `effective_date` |
| `salary_history` | **Immutable** ledger of every change. | `employee_id`, `compensation_id`, `change_type`, `previous_amount`, `new_amount`, `previous_/new_currency`, `previous_/new_frequency`, `increment_percentage NUMERIC(9,4)`, `increment_amount`, `effective_date`, `reason`, `changed_by` → users, `created_at` |
| `exchange_rates` | HR-maintained rates. | `base_currency`, `target_currency`, `rate NUMERIC(18,8)`, `effective_date`, `source` (description), unique(base, target, date) |
| `users` | HR logins. | `email` (unique), `password_hash` (bcrypt), `is_active` |
| `audit_logs` | Who did what. | `user_id`, `action`, `entity_type`, `entity_id`, `details JSON`, `created_at` |

`compensation` (current) and `salary_history` (past + present) are deliberately separate: reads of "current salary" stay a simple join, while history is append-only and never overwritten.

## Constraints
- **Uniqueness:** `employees.employee_code`, `employees.email` (stored lower-case), `compensation.employee_id`, `exchange_rates(base,target,effective_date)`.
- **Money:** `CHECK (amount >= 0)` on `compensation` and `salary_history`; `NUMERIC(14,2)` (never float).
- **Domains (CHECK):** currency ∈ {INR,USD,EUR}; frequency ∈ {annual,monthly,hourly}; employee `status` and `employment_type`; `change_type`; `rate > 0`; `base_currency <> target_currency`; `manager_id <> id`.
- **Foreign keys:** `ON DELETE RESTRICT` for compensation/history → employees (an employee with pay history cannot be deleted); `manager_id` is `SET NULL`.
- **Immutability:** a `BEFORE UPDATE OR DELETE` trigger on `salary_history` raises `salary_history is append-only`. The application also has no update/delete path. (`TRUNCATE` is intentionally not blocked so test/dev resets work.)
- **Sequence:** `employee_code_seq` (starts 100001) generates codes `ACME-<n>` for employees created in the UI; seeded employees use `ACME-00001…10000`, so the ranges never collide.

## Indexes
| Index | Serves |
|---|---|
| `employees(department_id)`, `(country_id)`, `(status)`, `(designation)`, `(joining_date)` | directory filters / sort |
| `employees(last_name, first_name)` | default name sort |
| unique `employee_code`, `email` | ID/email lookup, uniqueness |
| `employees(manager_id)` | reporting lines |
| `compensation(currency)` | currency filters/aggregates (+ unique `employee_id` for the join) |
| `salary_history(employee_id, effective_date, id)` | profile history timeline |
| `salary_history(effective_date)` | trends, recent changes |
| `exchange_rates(effective_date)` | latest-rate lookup |
| `audit_logs(entity_type, entity_id)`, `(created_at)`, `(user_id)` | audit queries |

Name search uses `ILIKE '%term%'` (wildcards escaped) across name, code and email. At 10,000 rows this is a few-millisecond scan; for far larger tables add a `pg_trgm` GIN index (see decisions.md).

## Annualisation (for cross-frequency comparison)
`annual = amount × {annual:1, monthly:12, hourly:2080}`; then `× rate` to the reporting currency. Done in SQL by one reusable expression, so filters, sorting and analytics always agree.
